# Session 2 Project Reasoning Round Table

Purpose: make the second half of every class a low-friction studio reasoning clinic that feeds directly into A1-A4.

This is not a formal presentation sequence. It is a recurring practice of showing one material from a student's own project and explaining how they understand the evidence, tool, workflow, threshold, or package decision behind it.

## Core Format

Every Session 2 uses the same basic protocol:

1. **Upload one material** to Slack before Session 2 starts.
2. **Speak for 60-90 seconds** from the material.
3. **Answer one focused question** from the instructor, peer, or room.
4. **Write one next action** that feeds the current assignment.

The material can be rough:

- plan, section, render, massing image
- precedent image
- site photo
- sketch
- spreadsheet table or chart
- GIS map
- GH canvas
- BIM/BEM screenshot
- Python notebook output
- AI prompt/output/check note

## Speaking Template

Students should not prepare formal slides. They should use this structure:

```text
I brought ________.
I chose / questioned this tool or evidence because ________.
Right now I think it supports ________, but it does not yet show ________.
My question to the room is ________.
```

For tool-choice weeks, use:

```text
I chose / rejected ________ because my design decision depends on ________.
The reasoning of the tool, as I understand it, is ________.
The output I need is ________.
The part I am least confident about is ________.
```

## Selection Protocol

Use a transparent selection system so participation is distributed without making the activity feel punitive.

- Volunteers go first and receive participation credit.
- If not enough people volunteer, use random draw.
- The draw selects materials, not performances.
- Students may pass once per semester if the material is genuinely not ready, but they still submit the Slack material and written next action.
- Instructor can curate one or two examples when a specific weekly concept needs to be visible.

## Weekly Assignment Mapping

| Week | Session 2 focus | Student brings | Check-in question | Assignment component fed |
|---:|---|---|---|---|
| 1 | Prior decision and original evidence | one image/diagram from a past project | What decision is visible here, and what evidence did you think supported it? | A1: Prior Studio Decision + Evidence Recall |
| 2 | Weak evidence and overclaim | same decision, with evidence marked | What does this evidence actually support, and what does it not show yet? | A1: Evidence Critique |
| 3 | Comparison logic | table, chart, or rough matrix | What variants/scenarios could be compared, and what would make the trade-off visible? | A1 final board + A2 Decision Recap |
| 4 | Spatial evidence fit | site map, plan, context image, or route diagram | Does this decision depend on location, distance, overlap, boundary, or access? | A2: Evidence Map + Tool Translation Matrix |
| 5 | Model/performance assumptions | BIM/BEM screenshot, section, envelope image, or performance claim | What would a performance model need to know, and what would it probably simplify? | A2: Tool Translation Matrix + Workflow Feasibility |
| 6 | Pathway and A4 branch | workflow sketch or branch declaration | Which route are you choosing, and what is the smallest useful output? | A2: Primary Workflow Selection + A4 Branch Declaration |
| 7 | Prototype logic | workflow artifact, canvas, notebook, spreadsheet, map, or screenshot | What goes in, what varies, what comes out, and what quality check proves it ran? | A3: Prototype Scope + Workflow Description |
| 8 | Verification and documentation | prompt log, error, output, README fragment, or checklist | What must someone else inspect before they trust this output? | A3: Verification and Failure Log |
| 9 | Threshold and recommendation | figure, output, table, or object-card draft | What result changes the design action, and what uncertainty remains visible? | A3 Output + A4 Practice Case/Object Card |
| 10 | Draft package gap | draft presentation, object card, or package outline | Can a reviewer trace decision -> variants -> workflow -> output -> threshold -> limit? | A4 Draft Package |
| 11 | Final package check | final component draft or reproducibility capsule | Which A4 component is weakest, and what must be fixed before submission? | A4 Final Package |
| 12 | Transfer forward | final object card or reflection note | What design reasoning can transfer to another studio project? | A4 Reflection Note |

## Why This Matters

This structure keeps the course MArch-first:

- students work from their own studio material every week;
- tool choice becomes architectural reasoning, not software sampling;
- speaking is frequent but low-stakes;
- assignment development happens in class instead of being hidden until deadlines;
- the instructor can see where evidence logic is weak before final submissions.

## Minimal Slide Insert

Each weekly deck can use one short Session 2 slide:

```markdown
## Session 2: Project Reasoning Round Table

::: {.slack-card}
**Upload one material:** plan, render, table, map, workflow screenshot, prompt log, or draft figure.

**Speak for 60-90 seconds:**

1. I brought...
2. I chose / questioned this evidence or tool because...
3. It supports...
4. It does not yet show...
5. My question is...
:::
```

Then add the week-specific check-in question from the mapping table.
