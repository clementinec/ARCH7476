## Class Protocol To Insert Early

Add this to Week 1, then repeat in shorter form in later weeks.

### Participation and Round Table

- We begin with round-of-the-room discussion, not waiting for volunteers.
- Each student should be ready to speak briefly about their own project.
- Volunteering to present or respond counts as class participation.
- If you speak up substantively, that can satisfy participation for that session.
- If you do not speak voluntarily, expect to be called during the round-table.
- The point is not performance. The point is making each student's evidence logic visible.

### Two-Part Class Format

Every class should show:

```text
Session 1: Lecture / Demo
BREAK TIME
Session 2: Round Table on YOUR [evidence / tool / workflow / threshold]
```

### Round Table Ground Rules

- one project
- one decision
- one evidence claim
- one thing still vague
- one next action

### Slack Visual Sharing

Session 2 should use Slack to lower presentation friction.

Students upload one rough visual before the round table:

- screenshot
- render
- diagram
- table
- photo of sketch
- GIS map
- GH canvas
- spreadsheet chart

The presentation format is:

1. send the image
2. speak for 60-90 seconds
3. answer one evidence/workflow question

This should feel like project sharing, not a formal presentation.

### Session 2 Reflection

Every Session 2 should end with a short reflection:

- What from Session 1 changed how I see my project?
- What changed in my evidence logic?
- What is still vague?
- What is my next action before the next class?

## A1 Timing To Insert

A1 should be described as a three-week arc.

```text
A1 lasts three weeks.

```

## Concrete "Vibes vs Evidence" Examples To Add

Use some non-architecture examples so students understand the logic quickly.

| Vibe claim | Why it is not yet evidence | What evidence would strengthen it |
|---|---|---|
| "This restaurant feels popular, so the layout works." | atmosphere and crowd impression are not a measured use pattern | dwell time, table turnover, observation by time period |
| "This phone must have a good camera because the ad looks professional." | marketing image is not camera performance | side-by-side test images, sensor specs, low-light comparison |
| "This medicine works because one friend recovered after taking it." | anecdote confuses timing with causation | clinical trial, control group, dosage and side-effect data |
| "This route is safer because it feels calmer." | perceived calm may miss accident or lighting risk | collision data, lighting levels, pedestrian counts, user survey |
| "This investment is safe because everyone is buying it." | popularity is not risk evidence | volatility, fundamentals, downside scenario |
| "This facade is sustainable because it is green and shaded in render." | image style is not performance | solar exposure, heat gain, daylight, material data |
| "This public space works because the precedent photo is lively." | one curated image may hide time, weather, management | observation schedule, occupancy counts, activity mapping |
| "This AI render proves the design atmosphere." | generated image can invent plausibility | source geometry, prompt log, material/lighting checks, user critique |
