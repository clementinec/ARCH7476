The core idea

Minimal Viable Workflow

A prototype is successful — even when rough — if it can do four things:

What “working” means Take real inputs, run a clear process, produce one interpretable output, and reveal where the method still breaks.

  • it does not need to be polished
  • it does not need to be complete
  • it needs to be legible enough that someone else could rerun it

The prototype frame — four zones

Read any workflow as four zones. If you can fill all four honestly, you have a prototype, not just a file.

Input the real files, data, or model the method starts from

What varies the one thing you change between runs

Output the single interpretable result it produces

Quality check what proves the run was valid, not just that it ran

Grasshopper translation

A GH component is a packed function

Reproducibility lessons from practice

The common failures are not about talent — they are about traceability.

  • the analyst leaves and no one can rerun the method
  • the spreadsheet works on one machine only
  • the GIS layers were clipped somehow but nobody recorded how
  • the notebook runs, but only if you know which file was silently edited

If the workflow cannot be retraced, the result is hard to trust — no matter how good the output looks.

Where the gaps usually hide

Typical first-draft descriptions sound like this:

  • “I used some plugin, but I forgot which one.”
  • “I changed the settings until it looked right.”
  • “The chart came from another file, I think.”
  • “The model worked last week.”

Each of these is a missing line in one of the four zones. Naming the gap is the first repair.

Many valid routes

There is no single correct technical route

Six routes, same four zones. None is more “advanced” than the others — each is judged only by whether the loop is legible.

Spreadsheet In comparison table · Varies parameter ranges · Out ranked options · Check formulas auditable, units stated

GIS In layers + CRS · Varies operation sequence · Out spatial comparison · Check CRS stated, counts spot-checked

Python / notebook In data files + paths · Varies analysis parameters · Out figure / table · Check runs top-to-bottom, paths stated

GH / parametric In geometry + sliders · Varies the design space · Out comparable variants · Check variants share assumptions

BIM/BEM / simulation In model + settings · Varies scenario assumptions · Out performance result · Check dominant assumptions documented

AI-assisted In prompt + source data · Varies what AI generates / edits · Out drafted component · Check a manual review confirms it

Pick the route that makes your decision more defensible — not the one that looks most impressive.

Run a reference kit Several routes have a clone-and-run starter: spreadsheet · GIS · simulation proxy · Python notebook · AI-assisted. Start from one and swap in your own decision.

Studio-lab · do this now

Documentation Swap

Do this now

  1. swap instructions with someone using a different route
  2. no verbal explanation allowed
  3. try to follow their method
  4. record what is missing, unclear, or fragile

This is the fastest way to learn whether your workflow is genuinely reproducible or only familiar to you.

Documentation Reality Check

If another student cannot follow your documentation, the method is not yet ready for A3.

That does not mean the project is weak. It means the workflow needs one more layer of translation before someone else can inspect it.

Pathway breakout checks

Spreadsheet

  • which formula or chart is most fragile?

  • what layer preparation is essential?

  • what package, path, or file assumptions must be stated?

  • what model assumptions dominate the result?
  • what setup choices must be documented first?

  • what did AI generate or edit?
  • what manual check confirms the output is usable?

Uncertainty check

A working prototype can still be wrong

Question for your A3 What is the smallest input change that would make your prototype output visibly different?

If no visible change appears, either the workflow is not sensitive enough, the output is not meaningful, or the connection is broken.

Capture the decision logic too

Do not document only button clicks. Also capture the reasoning:

  • why this step exists
  • what assumption it encodes
  • what judgment call it contains
  • how the output connects back to the question

A workflow becomes evidence when the reasoning travels with the steps, not just the clicks.

Mentor prep

Use the prototype to ask sharper questions

The point of a rough prototype is that it surfaces real questions for your mentor.

  • where is the workflow weakest?
  • what assumption am I least confident about?
  • what output would most strengthen the project?
  • what would a practitioner immediately ask about?

Mentor question development

Write three questions

  1. one technical question
  2. one methodological question
  3. one strategic question about scope or decision relevance

If the question is generic, it is not ready. A good question points at a specific zone of your loop.

Prototype Quality Check

The test for “ready for the round table”:

Input can another person tell what goes in?

What varies can they see which judgment calls mattered?

Output can they tell what comes out?

Quality check can they tell whether the output is already useful?

Mode 1 — the walk-through (optional, celebrated)

Teach us your strongest route A volunteer runs the class through one prototype they know well — uninterrupted, 3–4 minutes. Speak for roughly 60–90 seconds on the loop itself.

Narrate the four zones as you go:

  • what goes in (input)
  • what varies (the one thing you change)
  • what comes out (output)
  • what quality check proves it ran (threshold)

No polish required — show the real thing working. Questions wait for Mode 2.

Object this week: your prototype workflow as someone else will meet it.

Did What does the workflow actually do, step by step?

Assumed What hidden inputs or settings does each step assume?

Risk Where did I not check — where could it break or fail to rerun?
